# CC-011 — Gmail provider response handling and controlled live list acceptance

Implemented and verified, 2026-11-10. User authorized investigation of a provider
sync failure with one-hour/10-message/one-page bounds and no mailbox modifications,
application submissions or code entry. Initial HEAD `a1841341`, clean tree.

## Exact cause and evidence

Initial local inspection read only redacted health/counts: failed sync, no
successful checkpoint. Old generic errorCategory=provider did not identify the
request/parse stage. Added diagnostics, then the user explicitly ran the controlled
command and supplied its output. The actual Gmail message-list request returned
HTTP 204 No Content; response.json() on that body threw, producing a parsing
failure subsequently collapsed into provider. OAuth/scopes/account verification
had already passed. This was not an OAuth, credential or permission rejection.

The old partial-response field selection omitted resultSizeEstimate. Adding it
retains the zero-result indicator when no message IDs/page token are present.
The subsequent user-run actual Gmail list returned HTTP 200, response_validated,
and idle/incomplete=false. A read-only, redacted local health inspection then
confirmed the provider's complete checkpoint. No raw API body, message ID,
headers, addresses, credentials, authorization codes or tokens were copied into
shared docs/logs. The historical HTTP 204 parse bug is confirmed; Gmail's internal
reason for choosing that status is not independently asserted.

## Changes

- Gmail list selects messages(id),nextPageToken,resultSizeEstimate. HTTP 204 is
  handled before JSON decoding. A bare/no-content or uninformative JSON response
  is conservatively incomplete, not proof of an empty complete window. Explicit
  zero-result JSON can complete the bounded window. Inconsistent estimates,
  malformed collections and parser errors cannot advance a checkpoint.
- `gmail-diagnostics.mjs`: fixed stages/categories/reason codes and optional
  numeric HTTP status. No raw errors/provider descriptions, request URLs/IDs,
  headers, message text, codes or tokens. Parsing, permission, request and local
  synchronization/publication failures are separately inspectable. Safe API
  failure codes remain compatible with OAuth account-verification diagnostics.
- Adapter emits request/response validation events without query/identity values.
  Coordinator exposes a sanitized syncDiagnostic for Gmail failures, including
  observation persistence or checkpoint conflicts. Outlook defaults unchanged;
  existing CAS/replay/dedup/source-account boundaries preserved. Failed and
  ambiguous results retain the previous successful checkpoint and never retry.
- Gmail initial-sync wrapper and adapter now enforce one hour maximum (not merely
  a one-hour default), 10 IDs and one page. No scope or permission expansion.
- Added explicit -a/-d aliases and `npm run gmail -- -a -d` to avoid shell line/
  filename wrapping errors observed during user retries. Authorization is never
  implied by diagnostics or the npm script; -a is still mandatory. No default
  background operation, code use, application status change or submission.
