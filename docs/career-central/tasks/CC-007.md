# CC-007 — Explicit interrupted mailbox sync reconciliation

Implemented locally, 2026-11-10, after CC-006 checkpoint `7ca248e4`.
No live mailbox or credential was accessed.

`lib/email/sync-recovery.mjs` reads bounded, validated owner metadata and exposes
redacted recovery status. An explicit abandonment operation requires the exact
run ID, current expected revision and acknowledgment that the original worker
has stopped. It identifies CC-006 runs by their recorded start operation and
syncing state. Nonmatching, legacy or stale state is refused.

The existing mailbox owner writer performs the final revision check under its
lock. Abandonment records failed/incomplete with an unknown error category,
preserves account/scope/connection/checkpoint/last-success and application data,
and clears scheduling metadata while retaining the retry attempt count. No
inspection callback, observation write, mailbox read or application action is
invoked. A later sync must be separately invoked with a fresh run ID.

CLI (data root resolved through `path-resolver.mjs`):

```sh
node scripts/outlook-sync-recovery.mjs status
node scripts/outlook-sync-recovery.mjs abandon --run-id RUN_ID --expected-revision REVISION --acknowledge-worker-stopped
```

Status is read-only and creates no directories; it excludes account IDs and
raw ledger contents. Errors use a fixed allow-list. Abandonment never claims
completion or retries observations. Repeated/stale requests stop without writes.
Do not run abandonment while a worker remains active. The acknowledgment is a
human assertion; no process lease or independent liveness verification is
implemented. Review persisted state after any uncertain publication outcome.
