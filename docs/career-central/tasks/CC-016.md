# CC-016 — Priority job monitor and rapid preparation queue

Status: planned early core product release, not started or activated. Milestone P1b. Requirements R02/R03/R06/R07/R09/R10/R13/R16/R17/R18; F55–F59. Depends only on the minimum shared eligibility/identity contract from [CC-015](CC-015.md), not full AI matching, autonomous submission or cloud hosting.

## Smallest useful implementation

Monitor 3–5 user-approved high-priority employers through supported Greenhouse/Lever/Ashby feeds. Reuse existing provider registry/HTTP helpers, scan/dedup/liveness, matching, scheduler store/runner, canonical projection and application planning. The user chooses sources; do not bake employers or personal facts into shared code. Prioritize subsequent Workday, iCIMS, SmartRecruiters and official-page coverage source by source, subject to API/policy/access constraints.

User journey: monitor status → new qualified posting → one actionable dashboard alert → one local preparation proposal → review missing eligibility/facts/document approval → separately authorized supported application workflow. No silent browser launch, employer form access/upload, resume replacement, email/desktop/push send or submission from a monitoring event.

## Scheduling and source health

Private configuration defines employer identity, provider/feed, enabled/paused state, priority, desired interval, source limits and schedule/quiet-hours behavior. Desired targets are high 5 minutes, medium 15 minutes, general 30–60 minutes; actual cadence is bounded by upstream policies, worker uptime and global/per-source budgets. Existing scan installer cadence is 15 minutes, so it does not establish five-minute monitor support: design/test a compatible bounded tick/nextDueAt mechanism without installing/activating it implicitly.

Use bounded requests, concurrency caps, timeouts, conditional GETs where supported, jitter, exponential backoff/Retry-After and adaptive intervals. Persist nextDueAt, last attempted/successful check, response/unchanged/failure state and sanitized reason. Skip unsupported/restricted sources rather than bypassing them. An unchanged feed should not trigger evaluation/alerts/preparation again. Respect pause/STOP and graceful shutdown; show missed/delayed polls and overdue sources honestly.

## Identity, timestamps and change events

Represent employer/source + stable provider/requisition ID and canonical URL; retain aliases and content hash/version. Store firstSeenAt separately from nullable employerPublishedAt and published-time provenance/confidence. Also retain lastSeenAt/lastChangedAt and source completeness. Never infer published time from discovery, a failed request or an updated timestamp.

Emit distinct events for newly discovered (publication unknown), verified newly published, changed, repost-related, expired and duplicate. A first snapshot establishes a baseline; do not notify every historical listing as new. Offer an explicit bounded baseline summary/review instead. An omitted row on a failed/partial response cannot establish expiry. Define/test a source-specific expiry policy (explicit expiry or corroborated complete successful snapshots) and preserve repost/prior-application relationships. An updated job only retriggers evaluation on relevant version change, not timestamp noise.

## Durable event/task/alert contract

Extend existing owned source/scheduler/projection contracts deliberately; do not put credentials, raw email or a competing application tracker into monitor state. Specify monitor definition/checkpoint/event and preparation-proposal owners and migration/version checks before implementation. A generic worker-health record is not a source checkpoint. Stage durable change events and downstream task/alert intents before committing the source checkpoint; a crash between stages must replay safely with stable idempotency keys.

Use source+posting+meaningful version/event for processing identity. Lease/claim fences prevent competing workers; recover stale claims under the existing owner lock. Test baseline, first change, persistence uncertainty, shutdown and restart at each publication stage. Do not promise exactly-once external effects from a file lock. Local durable alert/task dedup is sufficient for the first slice; future external channels need an outbox and uncertain-delivery semantics.

## Immediate evaluation and rapid preparation

Use the user's current verified role weights/entry-level/graduation policy through the existing profile, not monitoring-specific constants. Evaluate graduation/start, geography, requirements, resume match, compensation/unknowns, gaps and prior application/requisition history before priority. Record method/profile/description versions and reasons. Unknown essential eligibility or conflicting history blocks automatic readiness even when score is high.

A high-priority match creates one local PreparationProposal with job/event identity, candidate approved resume/version/hash if suitable, verified answer references, required employer questions or “not yet inspected,” missing information and approval requirements. Do not claim complete form readiness without authorized inspection. Reuse an approved version; any new tailoring/fact edit requires review. Unsupported ATS goes to manual review, not a generic submit adapter. Eventual policy-authorized background preparation must retain its own permission/lease and expiry checks.

## Notifications and analytics

First channel: persisted dashboard inbox using the existing Next.js/projection UI, with read/dismiss/snooze/mute states. Alert includes company/title, location, salary or unknown, score/method, verified publication time or unknown, discovery time, readiness and outstanding approvals. Suppress duplicate event/channel alerts, coalesce changes and respect quiet hours/digests. Desktop, PWA push and optional email are later separately authorized transports; first-slice code must not send them.

Track daily discoveries, eligible/unknown/excluded and high-priority counts, source errors/availability, unchanged responses, scheduled-to-start poll lag, last-success freshness, and event-to-alert/preparation-ready times. Publication-to-discovery latency is nullable and only computed with trustworthy timestamps; report coverage and clock anomalies, not guessed zeros. Discovery-to-confirmed-submission requires actual receipt/owner events; pending cases remain pending/censored. Attribute eventual applications to monitor event/task IDs, distinguishing proposals, dispatches and confirmed receipts.

## Acceptance and activation gates

Offline injected-clock/fetch/store tests must demonstrate: per-priority next-due targets without exact timing promises; budgets/backoff/jitter/Retry-After; conditional unchanged responses; bounded malformed/partial/source failures; baseline versus new/updated/reposted/expired/duplicate classifications; timestamp uncertainty; profile/eligibility/prior-application checks; one alert/proposal per relevant event; competing workers and crash/restart checkpoint integrity; graceful pause/stop; sanitized health metrics; no employer browser/upload/message/submit activity. UI fixtures show readiness/unknowns, source outage and alert dispositions.

After offline acceptance, request explicit activation of exact employer feeds, request/cadence budget, duration, retention and dashboard alert behavior. Start with one bounded live cycle before authorizing recurring operation. Demonstrate one controlled posting change or honestly report no change; do not manufacture live novelty. Prove stable subsequent cycles and restart behavior without duplicate alerts. No broad crawl or five-minute schedule is enabled by this plan.

Future autonomy requires the separate P9 pilot: verified eligible/threshold-satisfying event → complete approved-policy payload → one dispatch → receipt/reconciliation → canonical tracker update → result notification. Uncertainty, verification challenges, changed facts/documents or expired authority stop dispatch. Preserve kill switches and all application gates.
