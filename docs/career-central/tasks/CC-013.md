# CC-013 — Bounded incoming reply context

User reports the reviewed test reached the original mailbox, initially in Junk.
This is user-reported send/delivery acceptance, not an independent agent mailbox
check or evidence of general recruiter deliverability. User requested continued
reply development and a reusable personal writing guide.

`npm run gmail:reply -- -a` uses the existing readonly OAuth and Gmail adapter.
It lists one page of at most ten messages from the latest hour, offers eligible
metadata for explicit selection, then reads only one selected body. It never
follows a cursor, updates sync checkpoints or changes application status.

Default test mode requires the configured original sender/receiving recipient,
the exact test subject (with Re prefixes) and a fixed “Test received” acknowledgment.
Only that acknowledgment becomes private context; quoted text and instructions
under it are discarded. A fixed test draft is prepared for separate SEND review.
No test job or fake application observation is created.

`--job-key` instead requires an existing job/exact sender rule. It reuses envelope
and application-mail analysis for direct Gmail or redirected original-recipient
mail. Security/verification content is excluded, numeric sequences of 6–10 digits
are redacted from private drafting context, and only one matching job is used.
Thread ID/Message-ID come from the selected GET; an alternate Reply-To is refused.
Header signals do not prove sender authenticity. The user still reviews recipients
and final prose. There is no model API or autonomous reply worker.

Private context/drafts stay outside Git with owner-only files. Shared summaries
contain state/counts only. The personal writing guide and samples stay in the user
layer and are linked from standing custom instructions; shared docs do not contain
the user's prose/profile or private source paths. The guide distinguishes fiction
research findings from editorial applications to professional writing.
