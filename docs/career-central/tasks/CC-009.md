# CC-009 — Dedicated Gmail receiving integration

Implemented locally, 2026-11-10. User authorized code development and named a
receiving Gmail/original MSN mapping, but explicitly withheld connection access.
Personal addresses are intentionally absent from shared docs/source; the local
setup command records them in private configuration after a desktop client JSON
is available. No actual private config, token, account or mailbox was opened or
modified. Initial Git state: `92b7e0d9`, clean tree.

## Result

- `gmail-auth.mjs`: Google's official OAuth library; browser authorization code
  flow, PKCE/S256, random state and IPv4-only loopback. Connection requires an
  explicit runtime authorization flag; imports/setup never sign in. Online-only
  tokens stay in process memory; unexpected refresh tokens are discarded. The
  granted scope must be exactly Gmail readonly, audience must match the desktop
  client, and a readonly Gmail profile request must match the receiving account
  before message access. Errors are category-only; SDK credentials are cleared.
- `oauth-loopback.mjs`: bounded callback helper with five-minute timeout, state,
  single code, denial and one-use guards. No credential/token logging or public
  interface binding. Outlook's existing OAuth implementation is preserved.
- `gmail-client.mjs`: internally constructed GET-only profile/list/detail URLs;
  redirects refused, one page/10 IDs, at most 10 metadata/10 selected detail reads.
  Gmail internalDate enforces the exact bounded window after a coarse-second
  search superset. Next-page tokens are neither followed nor exposed. RFC address
  parsing, duplicate-header rejection, bounded UTF-8 MIME/HTML decoding and no
  attachment/nested-email fetch/rendering. No send/modify/delete/settings method.
- `gmail-configuration.mjs`, `gmail-sync.mjs`, `gmail-email.mjs`: offline setup and
  exact sender rules, explicit `--authorize-connection`, original-recipient vs
  receiving-account distinction, one-hour default and 24-hour ceiling. Normalized
  redirects reuse the existing analyzer and bounded coordinator. Body text in
  ordinary forwards is never promoted to trusted original envelope metadata.
  Preview writes no ledger records; first-sync persists review-only observations.
- Shared coordinator/publisher/recovery: closed `outlook`/`gmail` provider slots
  under the existing ledger lock. Default Outlook `mailboxHealth` remains intact;
  Gmail uses schema-v2 `gmailMailboxHealth` with independent account/revision/
  checkpoint/replay history. Recovery cannot cross provider slots. The Gmail
  operational identity/dedup namespace derives from its private setup nonce plus
  receiving and original addresses, blocking silent checkpoint reuse after an
  address edit. No second tracker/database or source-of-truth migration.
- Shared analyzer: optional original-Date freshness checks for redirects;
  obvious account-security subjects are rejected before detail reads. Existing
  body exclusions and exact application verification-session checks remain.
  Evidence writer selects `gmail_api` explicitly; Outlook retains microsoft_graph.
  Codes, bodies, subjects, addresses, tokens and page tokens are never retained
  in observations. Status changes, code use and submissions remain disabled.
- New user runbook [GMAIL.md](../../GMAIL.md) describes free Google Cloud setup,
  private JSON/config, selective Redirect to rules and consent-gated first read.

## Credentials and dependencies

Desktop JSON must be owner-private and outside all Git checkout paths. Config is
in a separate outside-Git Gmail state directory. Symlink/hard-link/broad-mode
files and Web/service-account clients are rejected. No token is written to disk
or environment. WSL needs no persistent vault for this session-only path; native
Windows uses the existing DACL guard and remains platform-unvalidated. No custom
crypto, app password, plaintext-token fallback or Microsoft credential access.

Installed exact direct dependencies `google-auth-library` 11.3.4 and
`email-addresses` 5.0.0 with scripts disabled. Root lockfile remains ignored under
existing policy. npm audit reports two moderate findings in the pre-existing
MSAL/uuid dependency chain; none reported in the newly added Gmail dependencies.
No force/major MSAL upgrade was applied, preserving the existing Outlook line.
Registry/install traffic was not OAuth or mailbox access; no Cloud resource,
billing account, tenant, forwarding rule or service was created.

## Next step and limits

User must create an External/Testing Desktop OAuth client with only
`https://www.googleapis.com/auth/gmail.readonly`, add the dedicated account as a
test user and privately save the downloaded JSON, with billing disabled. Offline
`init` binds receiving/original addresses. Then wait for explicit connection
permission before any sign-in/profile/list/detail request. Initial authorized
acceptance should use one hour/10 IDs and start as metadata-only without guessed
sender rules. No paid services or Microsoft authentication is needed.

Use Outlook's Redirect to, not ordinary inline/attached forwarding, for intact
headers; actual redirected headers and sender provenance remain unvalidated.
Missing/ambiguous dates, unsupported encoding/MIME or templates require manual
review. This is English-oriented review classification, not proof of sender
identity or receipt authenticity. Short-lived codes can expire during forwarding.
No automatic code entry/status transition/submission/background loop exists.
The current dashboard mailbox card remains Outlook-only; Gmail health is local
CLI metadata until a separately scoped presentation update. Raw mail is never a
candidate-fact source. All original application approval/kill-switch gates remain.
