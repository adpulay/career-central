# Job monitor owner extension v1

Explicitly invoked local core: `job-monitor.mjs`, `monitor-feed.mjs`; [runbook](../../docs/JOB_MONITOR.md). No background activation on import/read or dashboard refresh.

The existing application-ledger owner (`lib/applications/store.mjs:updateLedger`) owns an additive `jobMonitor` namespace, with schemaVersion/revision and maps sources/postings/alerts/preparationTasks. Other top-level owners remain unchanged. This store is a derived source/shortlist/proposal index, not canonical applications; no monitor decision maps to Submitted/Applied. The existing scheduler remains unchanged and does not automatically run this component.

Source definition: opaque ID, supported provider/board, employer label, desired interval. Source operation: checkpoint checkedAt/provenance/conditional validators, claim token/expiry, due/attempt/success/error/cycle/quiet/backoff state. No credential fields, user-supplied arbitrary endpoint or execution grant. Built-in sourceFeed constructs supported URLs. A live CLI cycle requires explicit authorize-live-read; recurring execution is not installed.

Posting: hash of provider/board/native posting ID with employer requisition/canonical URL references; meaningful-content hash/version, first/last-seen, nullable employer timestamp/provenance, completeness-based absence count, availability, related-opening hint, source excerpt and heuristic match/profile digest. Original cache/provider content is not overwritten. Native posting IDs take precedence over requisition-group IDs so multiple distinct postings cannot be silently merged. Exact canonical URL aliases collapse duplicate slots. Same-title hints never authorize submission dedup bypass.

Matching reuses existing scanner admission and ranking, injecting private verified skills, role emphasis and separate status-aware canonical-history checks. Unknown essential metadata, start/availability, authorization or external-application history prevents readiness. Exact publication/graduation snippets are evidence signals, not independent authentication or a complete natural-language requirements parser. Snapshot data is untrusted input; no employer content becomes instructions.

The source cycle has three phases: locked durable lease; unlocked bounded provider read/normalization; locked fenced atomic postings + alerts + proposals + checkpoint publication. Stable posting-version event IDs deduplicate alerts; posting IDs deduplicate preparation proposals. A timeout/crash leaves a lease for bounded recovery; reclaimed tokens fence late writers. Incomplete/invalid snapshots do not publish partial records. Normal 304 updates source health without pretending to prove expiry. Uncertain persistence stays explicit.

Only plain data and decisions are persisted. Preparation proposals are not resumable employer sessions, approved answers or an action queue transport. They hold candidate approved-document hash references and missing/approval lists; byte integrity/approval/eligibility must be checked by the existing application workflow before any external preparation. No browser, upload, send, code use or submit capability exists here.

Read APIs initialize nothing and distinguish invalid/unavailable state from empty state. Local UI commands accept only existing monitor IDs and closed decision enums; property-own checks prevent prototype-key mutation. The three-MiB monitor budget and eight-MiB owner limit fail closed. A future retention/migration or scheduler integration needs a scoped task; no duplicate canonical tracker or general unconstrained metadata writer is introduced.

Tests: synthetic end-to-end feed/provider parsing, identity/cohort/unknowns/history, crash/reclaimed leases, checkpoint atomicity, no duplicate alerts/proposals, rate limits/deferred provider retries, cache-only provenance, decision persistence and real production-browser interaction. Native OS/cloud/live-source reliability are not certified by these fixtures.
